# Quota 多设备与双系统同步方案

2026-10-04 · 设计方案，未实现、未部署。暂按 Windows + macOS 设计；同步协议不依赖系统，可扩展 Linux。

## 异步同步的简化路线（后续讨论）

如果优先解决个人多电脑使用，推荐先抽离本地异步同步引擎，增加直接 WebDAV 传输；完整账号服务作为后续传输方式。现有共享目录已具备部分异步交换能力，但直接 WebDAV、加密及配对尚未实现。WebDAV 目标须为用户自己的受限 HTTPS 存储，服务兼容性需要实测。

客户端先保存指标和待发送版本，界面立即显示本地结果；后台将增量分成独立小包，按设备写入各自目录，其他设备定期拉取并去重。旧包不可原地修改，结算修正发新版本；不得直接覆盖共同数据库。对对象存储可使用条件创建避免覆盖，具体能力必须按所选服务验证，例如 [S3 条件写入](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)。扫描采用重叠发现与本地接收记录，不能只用本机时间作为分片发现游标，避免迟到包漏读。

网络工作与采集/报表分离，成功确认后清除对应发送版本；失败保留队列、退避重试，暂停、退出、休眠后可续传。界面显示待上传条数和最后成功同步，不阻塞模型选择及图表。应用不运行时不会继续同步。

可增加客户端加密分片；各设备通过已授权设备安全配对或用户保存的恢复码取得同步密钥，密钥保存在系统凭据存储，不直接放进同一云目录。需设计密钥恢复/轮换和跨设备删除；仅共享存储密码不能自动获得端到端加密。撤销存储访问也不能擦除旧设备已下载的内容。

这个路线能先免去 Quota 自建账号数据库和复杂部署，但需要用户准备兼容的存储及凭据；若产品要求“微信登录即同步、无需配置存储”，仍需认证、租户隔离和受限存储授权服务，可将统计分片放对象存储，仅维护轻量账号/设备元数据。异步引擎与数据协议保持一致，以后更换传输方式无需重写统计。

## 推荐路线

保留本地优先架构，在现有采集、SQLite、事件去重与修正版本之上增加账号云同步。共享目录继续作为可选方式。第一期完成 Token 用量和设备管理，第二期同步账户显示资料与快照，微信作为账号绑定方式接入。

结构：每台电脑只读本机日志 → 本地指标库与发送队列 → HTTPS 同步 API → PostgreSQL；其他电脑通过增量接口下载到各自本地库。不同系统不直接共享正在使用的 SQLite 文件、整份 config.json 或日志目录。

建议服务端使用 Rust/Axum + PostgreSQL，复用项目已有 Rust 经验。初期一个 API 服务、一个数据库和备份即可，不先引入 Redis、消息队列或 WebSocket。托管 PostgreSQL 可以减少数据库维护，具体服务商须在确定部署地区、网络与预算后选定。本方案不承诺某厂商免费额度或固定月费。

## 数据范围和合并规则

| 数据 | 第一阶段 | 合并方式 |
| --- | --- | --- |
| Token、工具调用、模型、时间、会话标识 | 同步 | 账号内事件 ID 去重，保留结算 revision；缓存、推理仍为子项 |
| 设备名称、系统、最后成功同步时间 | 同步 | 独立设备 UUID，名称可编辑，允许撤销设备 |
| 服务商账号显示名、平台、账户分组 | 第二阶段、用户选择开启 | 云端逻辑 account_id，与设备本地连接分开 |
| 余额、累计充值、累计消费、订阅额度 | 第二阶段、用户选择开启 | 带来源与采集时间的快照；同账号跨设备取最新有效值，不相加 |
| 手动金额、隐藏模型、本机价格覆盖 | 第二阶段、用户选择开启 | 按字段/条目版本更新，冲突提示；不自动覆盖已核实价格 |
| API Key、Cookie、Codex 登录令牌、AppSecret | 不同步 | 系统凭据存储；新设备单独连接服务商 |
| 对话、工具参数、本机路径、增量扫描游标 | 不同步 | 留在源设备；共享目录路径也不复制到其他系统 |

服务商账号不能按“同平台+同名称”自动认为相同；用户明确关联到同一逻辑账户。两台电脑连接同一个 GLM 账号的累计消费 100 元，合并仍为 100 元。两个不同账号的金额才可能合计，且需区分币种和统计口径。不能把本地 Token 换算成本当作官方累计账单。

## 登录和新电脑接入

第一阶段建议成熟的邮箱验证码/浏览器登录，提供新增设备流程；验证码需过期、单次使用、尝试限制和发送限流。已有微信应用条件尚未准备，不把微信审批作为同步协议的前置条件。

使用支持 OAuth/OIDC 的认证服务时，桌面端采用系统浏览器与 Authorization Code + PKCE，客户端不存认证服务的秘密。依据 [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)。微信另走其官方允许的授权流程：后端校验回调/state并交换身份，桌面端只领取绑定过期时间、单次消费和客户端挑战的 Quota 会话；不假定微信接口原生支持 PKCE。

微信 identity 绑定内部 Quota user_id，而不是直接把 OpenID 当跨应用账号。账号链接必须同时证明当前 Quota 会话和微信身份；已有绑定冲突不能自动合并。接入条件见 [微信云同步说明](wechat-cloud-sync.md)。

新电脑使用流程：

1. 安装 Quota，登录同一个 Quota 账号。
2. 命名设备，明确同意上传哪些统计；首次扫描和历史上传显示进度。
3. 下载已有设备统计，默认查看全部设备，也可只看当前电脑。
4. 本机重新连接需要余额查询的服务商；本地日志位置按本机系统配置。

二维码设备配对可后续加入：短期会话、已登录设备审批、单次消费、限流和撤销。它授权新设备的 Quota 会话，不传厂商密钥。

## 增量协议

建议接口：设备注册/撤销、批次上传、游标下载、同步状态、账号数据导出/删除。服务端从登录会话确定 user_id，每次校验设备归属，不能接受请求体 user_id 作为授权依据。

服务端建议表：users、identities、devices、usage_events、sync_changes。事件唯一键为 (user_id, event_id)，包括 source、origin/observed device、UTC 时间戳、model、指标、revision、schema_version 与内容摘要。revision 较低的修正不能覆盖较新记录；同 revision 内容冲突记录并返回待处理状态，不静默拼出一组不一致的字段最大值。

- 采集和写入发送队列同一事务。上传成功且收到逐条确认后，只删除对应队列版本；上传期间产生新修正不能被旧确认删掉。
- 上传可重试，服务端幂等合并；成功响应丢失后再次上传不重复增加统计。
- 下载先在本地事务内合并，再保存下载游标；崩溃后重复下载仍安全。按服务端已提交的同步序列排序，不依赖各设备时钟。服务端游标必须避免序号已分配但事务尚未提交造成漏读，可采用用户级串行事务分配提交序列。
- 初次同步分批回填允许范围的历史，恢复进度；不一次读取全部历史到内存。建议初期每批最多 500 条且压缩体积受限，依据实际指标大小调整。
- 云同步和共享目录需要独立确认状态；当前共享目录消费 outbox，不能直接让两种渠道共用一个会被清空的队列。
- 首次迁移明确来源与导入范围。已从其他设备收到的记录，不重新声明为当前电脑原始活动。

删除采用版本化删除标记。云端清空后，旧电脑的离线队列可能仍有历史；使用账号数据 generation 和重新确认流程，避免下次联网自动复活已删除数据。设备撤销会立即阻止之后的网络读写，但不能远程擦除已离线保存的数据；本地退出时提供保留/清除统计选择。

## 设备归属、备份和跨系统

同一台电脑的两个系统默认注册为两个设备，例如“工作电脑 · Windows”和“工作电脑 · macOS”；可归入同一设备组，但不共用身份令牌。跨机器恢复备份时生成新设备身份，不复制设备 UUID、会话、日志路径和扫描进度。

现有相同日志去重后使用较小设备 UUID 作为确定性归属，不能证明原始执行电脑。云端建议区分确定的源设备、观察设备列表和未知/复制历史；有明确来源才归属，无法判断的历史单独标记，保持总量去重。迁移需要保证旧事件 ID 连续；若调整 ID 规则，需版本和别名映射，不能直接重生成导致历史翻倍。还应验证 Codex 当前时间戳+累计计数 ID 在不同真实会话的碰撞风险，避免修复复制历史时误删独立活动。

原始事件使用 UTC 时间戳，账号内固定报表时区（初期默认 Asia/Shanghai、允许修改），各设备用同一规则聚合自然日；不能分别以本地时区汇总后相加。显示时标明报表时区。

客户端复用同一 React、采集和同步业务模块，平台差异集中到日志路径、主机名、系统凭据、启动/托盘、代理及更新安装。

当前 Cargo 已声明 Windows/macOS/Linux 的 keyring 后端，但不是 macOS 实机兼容验收。Windows 使用凭据管理器，macOS 验证 Keychain；Linux 后端与桌面密钥服务可用性另验收。另需处理 macOS 权限、休眠唤醒、网络切换、后台驻留，以及独立构建、签名和更新流程。

## 同步体验与离线

默认“本地可用”，登录并同意后才开云同步。页面显示最后成功同步、待上传条数、首次历史进度、连接失败及重试入口，不用一个长期旋转图标混淆采集和网络上传。

建议在线前台每 1–2 分钟交换增量，后台每 5 分钟；用户可关闭后台或选择立即同步。网络失败指数退避并加入随机延迟，不忙循环。应用退出、电脑关机或休眠时不采集；重开后补同步。要持续获取另一台电脑的本地活动，该电脑必须安装 Quota 并允许后台运行；单靠账号登录不能远程读取没上传的日志。

短期 Quota access token 放内存，刷新会话放系统凭据存储。用户切换账号时分开本地云数据、游标和上传队列；上一账号数据不能上传到下一账号。首次把未绑定本地历史归入账号需明确确认。

服务端 HTTPS、认证、请求限制、备份和最小权限是基础。按用户隔离数据库记录；可加 PostgreSQL RLS 作纵深防护，但应用连接不能用会绕过规则的表所有者/超级用户。参见 [PostgreSQL 行安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)。本期若只使用传输与磁盘加密，不称作端到端加密；端到端加密需另设计设备密钥分发、恢复与服务端检索限制。

## 落地顺序与验收

1. 固化协议与本地迁移：验证事件 ID、revision、设备身份、时区和账号隔离；为各传输方式分开队列确认。
2. 建立认证、设备管理及 Token 云同步：先用两台 Windows 验证，再用 Windows + macOS 验证相同事件总量。
3. 完成 macOS 发布与后台体验；保留共享目录迁移，云同步不是直接复制数据库。
4. 接入微信绑定；第二期同步可选的账户资料、快照、设置与冲突处理。

必须覆盖：离线追加后联网、重复批次、上传响应丢失、修正乱序、并发编辑、复制日志、独立会话同时间同用量、备份恢复、撤销设备、账号切换、清空后旧设备回连、跨时区与夏令时、休眠唤醒、首次大量历史、数据库恢复及旧客户端升级。

交付条件：两台设备与双系统一致的总量；源日志未改；凭据和对话不出设备；失败不丢队列；同一个服务商账号的金额不因设备数翻倍。确认部署地区、域名、认证运营和数据保留周期后再估算服务成本及工期，不把验证时间省掉。
